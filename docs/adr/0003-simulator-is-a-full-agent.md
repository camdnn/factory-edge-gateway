# The simulator is a full MTConnect agent behind the real edge

Scenarios (tool wear, feed interruption, alarm) exist to show the pipeline and the board reacting to trouble, so the simulator speaks the same protocol as a real MTConnect agent: `/sample?from=`, sequence numbers, a ring buffer and a new instance ID on every start. A second edge container reads it exactly as the first reads demo.mtconnect.org. We rejected having the simulator write straight to Kafka or having the consumer poll it, because either would demo a path no real machine takes and leave the edge's gap and restart handling untested. A side effect we want: restarting the simulator produces a real `GAP: agent restarted`. Scenarios are switched on the simulator itself, never from the status board, because a board that watches machines should not be able to command them.
