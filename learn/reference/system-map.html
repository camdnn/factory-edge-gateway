The code, file by file

internal/mtconnect/streams.go: reading the agent's XML

ParseStreams turns one agent response into a Header (the buffer bookkeeping: firstSequence, nextSequence, instanceId) plus a flat list of Observations. Each observation holds machine, component, data item, value, sequence and timestamp. It uses Go's encoding/xml with xml:",any" because machines report hundreds of differently named items. It also recognises the agent's error document (OUT_OF_RANGE). Tested against a saved real response in testdata/sample.xml.

internal/mtconnect/client.go: never skipping a reading

Client.Next(cursor) asks /sample?from=N&count=1000 and returns the new readings plus the next cursor. The cursor is {instance_id, next}. On first run it takes a /current snapshot instead. If the agent restarted (new instanceId) or we fell out of its buffer (OUT_OF_RANGE), it re-snapshots and reports gap = true. Data loss is never silent.

cmd/edge/main.go: the Pi program (Kafka producer)

  1. Load the cursor from /var/lib/edge/cursor.json.
  2. client.Next → readings. Log GAP if there was one.
  3. Send one Kafka record per reading, keyed by machine so each machine's readings stay in order in one partition.
  4. ProduceSync waits for Kafka to confirm (acks=all, idempotent producer). Only then save the new cursor, written atomically (temp file + rename).
  5. If the topic was recreated (UNKNOWN_TOPIC_ID), throw away the Kafka client and make a fresh one.

cmd/consumer/: the Mac program (Kafka consumer)

  • main.go: joins consumer group laptop, polls Kafka, saves each batch to SQLite, then commits the offsets. If saving fails it exits without committing, so Kafka redelivers. It reconnects on UNKNOWN_TOPIC_ID, and if Kafka lost data it re-reads from the start. It serves the status page on 127.0.0.1:8090 (your Mac only).
  • store.go: table observations with primary key (instance_id, sequence). A reading delivered twice is ignored (INSERT OR IGNORE), which makes replays harmless. Table latest keeps the newest value per data item so the page is fast.
  • index.html: the status board, one card per machine, polling /api/latest.

deploy/pi/: running it on the Pi

  • Dockerfile: compiles cmd/edge into a tiny static image.
  • docker-compose.yml: Kafka 4.1 as a single node (no ZooKeeper), plus the edge container.
    • Two listeners: INTERNAL (edge → Kafka inside Docker) and EXTERNAL (the Mac → Kafka over Tailscale, bound to the Tailscale IP only).
    • Retention: 24 h or about 2 GB.
    • Logs capped at 3 × 10 MB.
    • Data in the kafka-data volume.
  • .env (on the Pi only, not in git): the Pi's Tailscale name and IP. Kafka hands this address to clients, so it must be right.

The no-data-loss rules

HopRuleBookmark
agent → edgeadvance only after Kafka confirmsMTConnect sequence number (cursor.json)
Kafka → consumercommit only after SQLite savedKafka offset (stored in Kafka)
duplicatesignored by the databaseprimary key (instance_id, sequence)

Moving forward only after the next hop confirms means a crash can cause a repeat, never a skip. The database then ignores the repeats. This combination is often called effectively-once delivery.[ref]

Incidents: good interview stories

1 · Power loss → GAP

The Pi lost power for about 6.7 hours, but the agent only remembers about 45 minutes. On restart the edge saw its cursor was out of the buffer, logged GAP, and resumed from a fresh snapshot. The design worked: the hole was reported, not hidden. Side effects: the Pi's clock was wrong until it synced (it has no battery-backed clock), and one log line was corrupted. Lesson: shut down with sudo shutdown -h now.

2 · Kafka forgot everything on container recreate

Applying the log cap recreated the Kafka container, and Kafka came back empty. Cause: when configured through environment variables, the image leaves log.dirs unset. Kafka quietly wrote to /tmp/kafka-logs inside the container, not to the mounted volume. A reboot kept the data; a recreate deleted it. Fix: set KAFKA_LOG_DIRS explicitly, then prove it by force-recreating and checking the offsets survived. SQLite already had every record, so nothing reached-the-laptop was lost.

3 · Stuck forever on an old topic ID

After the wipe, the topic was recreated with a new hidden ID. Both programs kept using the old ID and got UNKNOWN_TOPIC_ID forever. Found by reproducing it locally: wipe Kafka in Docker on the Mac and watch. Fix: on that error, start a fresh Kafka client. Verified with a second local wipe: both recovered alone, and 17,961 sequences were stored with zero gaps.
