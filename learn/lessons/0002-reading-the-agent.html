Reading the agent without missing a thing

The edge program asks the MTConnect agent for data every second. By the end of this lesson you can look at the agent's header and the edge's saved cursor and say exactly what the edge will do next: carry on, or report a gap.

Warm-up from lesson 1

No scrolling back. Retrieval is the point.

Which program asks the agent for data, and where does it run?

Every response starts with a header

Here is the real header the demo agent sent on 21 October 2026. You can fetch a fresh one at demo.mtconnect.org/current.

<Header instanceId="1791887049"
        bufferSize="131072"
        firstSequence="34161250"
        lastSequence="34292321"
        nextSequence="34292322" />

Every observation the agent records gets the next sequence number. The agent keeps only the newest bufferSize of them in a ring buffer; when it is full, the oldest is overwritten.[1] So the header is the buffer's bookkeeping (streams.go parses it):

FieldMeans
firstSequenceoldest observation still in the buffer
lastSequencenewest observation in the buffer
nextSequencethe number the next observation will get, so where to ask from next time
instanceIdchanges whenever the agent restarts, which resets its numbering

Check the arithmetic: 34,292,322 − 34,161,250 = 131,072. The buffer is exactly full.

Two questions the edge can ask

RequestAnswerUsed when
/currentthe latest value of every data item, a snapshotfirst run, or after a gap
/sample?from=N&count=1000every observation from sequence N, up to 1000 of themevery normal poll

A snapshot only has the latest values, so it can skip changes. /sample returns every one, in order.[1] That's why the edge snapshots once, then follows with /sample forever.

The edge's memory between polls is the cursor: {instance_id, next}, saved to edge-cursor.json on the Pi only after Kafka confirms the write (you saw that rule in lesson 1).

The three outcomes of a poll

This is the heart of internal/mtconnect/client.go, trimmed:

switch {
case errors.As(err, &ae) && ae.Code == "OUT_OF_RANGE":
    // asked for sequences the agent already dropped
case err != nil:
    return cur, nil, nil, err          // network trouble: keep cursor, retry
case h.InstanceID != cur.InstanceID || cur.Next < h.FirstSequence:
    // agent restarted, or our sequences already left its buffer
default:
    return Cursor{h.InstanceID, h.NextSequence}, obs, nil, nil   // normal
}
// fall through: take a fresh /current snapshot and report a Gap
  1. No gapSame instanceId, and the cursor is still inside the buffer. Keep every observation, move the cursor to nextSequence.
  2. Gap: fell behind the bufferSame instanceId, but the cursor is older than firstSequence. The agent answers OUT_OF_RANGE; we fetched from=1 on the demo and got exactly that. The number missed is known.
  3. Gap: the agent restartedThe instanceId changed. Old sequence numbers mean nothing in the new numbering, so how many were missed is unknowable (Missed = 0).

In both gap cases the edge sends a gap record to the pipeline.gaps topic in the same batch as the observations, so a gap is always reported, never silent (see docs/adr/0001).

Practice: predict the poll

2. Cursor {1791887049, 34100000}

Try it for real (2 minutes)

In a terminal, ask the agent for something it no longer has, then for something it does. Use the firstSequence you see in the first command.

curl -s https://demo.mtconnect.org/current | grep -o '<Header[^>]*>'
curl -s 'https://demo.mtconnect.org/sample?from=1&count=1' | grep -o 'OUT_OF_RANGE'
curl -s 'https://demo.mtconnect.org/sample?from=FIRST&count=3' | grep -o 'sequence="[0-9]*"'

You just did by hand what Client.Next does every second.
